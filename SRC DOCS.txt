# 1. EXECUTIVE SUMMARY

## 1.1 Project Overview

Core Systems Hub is an internal web-based productivity, knowledge management, incident management, and work coordination platform designed for the Core Systems team.

The system will provide a centralized environment where staff members can:

- Document technical knowledge, projects, procedures, and completed work.
- Register and manage incidents reported through the Temenos support portal.
- Record daily work activities and automatically generate individual and consolidated reports.
- Create and manage departmental projects and individual tasks.
- Escalate unresolved incidents, technical blockers, and project delays.
- Monitor team activities, work progress, incident trends, and knowledge contributions.

The system will reduce dependency on scattered Excel files, individual documents, email conversations, and manually prepared reports.

It will also preserve institutional technical knowledge and make it accessible to authorized team members.

## 1.2 Main Objectives

1. Centralize technical knowledge and operational documentation.
2. Improve visibility of Temenos incidents and their internal handling.
3. Automate individual daily reporting and team report generation.
4. Improve project and task coordination.
5. Provide a structured escalation and follow-up mechanism.
6. Improve management visibility through dashboards and reports.
7. Preserve historical technical solutions and lessons learned.
8. Strengthen accountability, collaboration, and knowledge sharing.
9. Provide measurable evidence of team activities and project delivery.

## 1.3 Project Scope

The system consists of the following modules:

| Module | Main responsibility |
|---|---|
| Dashboard | Overview of team activities and important indicators |
| Knowledge Management | Technical knowledge, procedures, project documentation and lessons learned |
| Temenos Incident Management | Manual incident registration, assignment, investigation, tracking and resolution |
| Daily Activities | Individual daily work reporting |
| Report Generator | Individual, team, weekly, monthly and project reports |
| Project Management | Project creation, milestones, progress and ownership |
| Task Management | Task assignment, deadlines, status and completion |
| Escalation Management | Escalating incidents and internal blockers |
| Document Management | Secure attachments and shared technical documents |
| Team Management | User administration and permissions |
| Administration | Configuration, categories, templates and audit management |
| Analytics | Operational and management reporting |

## 1.4 Out of Scope for the Initial Release

The following are not included in the initial version:

- Automatic integration with the Temenos support portal.
- Replacing the official Temenos portal.
- Automatic monitoring of production T24 transactions.
- Automated T24 COB or EOD execution.
- Infrastructure monitoring and alerting.
- Full HR, payroll or employee performance appraisal management.
- Financial accounting and transaction processing.
- Automatic escalation through external communication systems unless separately approved.
- Replacing an existing bank-wide service-management platform.

Future integrations may be considered after the initial platform is stable.

Responsible for system administration.

Permissions:
- Manage users and roles.
- Configure permissions.
- Create and manage system categories.
- Configure report templates.
- Manage system settings.
- View audit logs.
- Manage all records when authorized.
- Manage application-wide access.

### TEAM_LEAD / MANAGER

Responsible for coordinating the team.

Permissions:
- View team dashboards.
- View submitted daily reports.
- Review and return reports for correction.
- Create and manage projects.
- Assign tasks.
- Monitor incidents.
- Manage escalations.
- Review and approve knowledge articles.
- Generate team reports.
- View team performance indicators.

### KNOWLEDGE_MANAGER

Responsible for technical knowledge quality.

Permissions:
- Review knowledge articles.
- Approve or reject submitted articles.
- Manage knowledge categories.
- Maintain reusable troubleshooting guides.
- Manage knowledge article versions.
- Monitor article quality.

### CONTRIBUTOR / STAFF

Responsible for daily operational activities.

Permissions:
- Create knowledge articles.
- Edit own permitted drafts.
- Register incidents.
- Update assigned incidents.
- Submit daily reports.
- Create or update assigned tasks.
- Create project updates when authorized.
- Raise escalations.
- Comment on authorized records.
- Upload permitted attachments.
- Search and read published knowledge.

### VIEWER

Read-only access to authorized content.

Permissions:
- View published knowledge.
- View authorized incidents and reports.
- View authorized projects and tasks.
- Download permitted documents.

## 2.2 Authorization Rules

Authorization must be enforced on the server.

Hiding buttons in the frontend is not sufficient.

Important rules:

1. Staff members can edit their own profile but cannot change their own role.
2. Staff members cannot change another user's permissions.
3. A contributor can edit only records for which they have permission.
4. Team leaders can access records within their authorized team scope.
5. Knowledge approval must be restricted to authorized reviewers.
6. Only authorized users can view confidential attachments.
7. Deleting users must not destroy their historical contributions.
8. Changes to roles and sensitive records must be audited.
9. Access to individual daily reports must follow configured reporting permissions.
10. Administrative actions must be checked by the backend on every request.

# 3. FUNCTIONAL REQUIREMENTS

# MODULE 1: KNOWLEDGE MANAGEMENT

## 3.1 Purpose

Provide a centralized repository where staff members document how they perform tasks, implement projects, solve technical problems, configure systems, and learn from experience.

Knowledge is a team asset and must remain available even when its original author leaves the organization.

## 3.2 Knowledge Categories

Proposed categories:

- Temenos T24 / Transact
- AA / Arrangements
- COB / EOD / SOD
- TAFJ / JBoss
- Oracle Database
- FCM / AML
- Integration and APIs
- Payments and Transfers
- Interest and Loans
- System Administration
- Infrastructure and Deployment
- Projects and Implementations
- Troubleshooting and Known Errors
- Operational Procedures
- Other

Administrators must be able to create additional categories.

## 3.3 Knowledge Article Fields

| Field | Required | Description |
|---|---|---|
| Article ID | Automatic | Unique identifier |
| Title | Yes | Knowledge article title |
| Category | Yes | Main knowledge category |
| Project / System | Optional | Related project or application |
| Module | Optional | T24 module or technical area |
| Summary | Yes | Short explanation |
| Objective / Problem | Yes | What was required or what problem occurred |
| Prerequisites | Optional | Requirements before implementation |
| Implementation Steps | Yes | Detailed procedure |
| Configuration / Technical Details | Optional | Technical configuration and code references |
| Challenges | Optional | Problems encountered |
| Solution | Optional | How the problem was solved |
| Verification | Optional | How successful completion was confirmed |
| Lessons Learned | Optional | Knowledge gained |
| References | Optional | Related incidents, documents or articles |
| Attachments | Optional | Supporting files |
| Author | Automatic | User who created the article |
| Reviewer | Automatic when reviewed | User responsible for review |
| Status | Automatic | Draft, submitted, approved, rejected, archived |
| Created Date | Automatic | Creation date |
| Updated Date | Automatic | Last update |

## 3.4 Knowledge Article Workflow

1. Staff member creates a new article.
2. Staff member selects a category and provides the technical information.
3. The article is saved as Draft.
4. Staff member submits it for review.
5. Knowledge Manager or authorized Team Lead reviews it.
6. Reviewer approves or rejects it.
7. Approved articles become searchable by authorized users.
8. Other staff members can comment, provide improvements, or rate usefulness.
9. Major changes create a new article version.
10. Old versions remain available to authorized reviewers.

### Article Statuses

- DRAFT
- SUBMITTED
- UNDER_REVIEW
- APPROVED
- REJECTED
- ARCHIVED

## 3.5 Knowledge Search

Search must support:

- Article title.
- Article ID.
- Category and module.
- Project name.
- Error message.
- Technical keywords.
- Implementation steps.
- Solution.
- Related TSR references.

Search should be fast and typo tolerant.

## 3.6 Knowledge Quality and Reuse

The system should track:

- Number of articles created by each staff member.
- Number of approved articles.
- Number of article views.
- Number of comments.
- Usefulness feedback.
- Articles linked to incidents.
- Frequently reused solutions.

Views and contributions are supporting indicators, not automatic measures of employee performance.

# MODULE 2: TEMENOS INCIDENT MANAGEMENT

## 4.1 Purpose

Provide an internal management interface for incidents received from the Temenos support portal.

Staff members manually register the incidents and maintain the bank's internal investigation, ownership, follow-up, escalation, and resolution information.

The official Temenos portal remains the source of the external support case.

## 4.2 Incident Registration

### Required Fields

| Field | Required |
|---|---|
| TSR Reference | Yes |
| Incident Title | Yes |
| Description / Problem | Yes |
| Temenos Module | Yes |
| Group | Yes |
| Subgroup | Optional |
| Priority | Yes |
| Severity | Yes |
| Date Reported to Temenos | Yes |
| Internal Owner | Yes |
| Current Status | Yes |

### Optional Fields

- Temenos assigned engineer.
- Temenos response reference.
- Root cause.
- Internal investigation.
- Actions taken.
- Solution / Fix.
- Verification.
- Notes.
- Related project.
- Attachments.
- Related knowledge articles.
- External portal link, where permitted.

## 4.3 Incident Status Workflow

Initial statuses:

- NEW
- ASSIGNED
- INVESTIGATING
- WAITING_FOR_TEMENOS
- WAITING_FOR_INTERNAL_TEAM
- RESOLVED
- CLOSED
- REOPENED
- ESCALATED

A record must retain its status history.

The system must distinguish between:

- Internal incident status.
- Official Temenos portal status.

The internal status must never be presented as the official Temenos status unless it has been verified.

## 4.4 Incident Lifecycle

1. Staff member receives or identifies a Temenos incident.
2. Staff member manually registers the TSR.
3. The system validates that the TSR reference is not duplicated.
4. An authorized user assigns an internal owner.
5. The owner investigates the issue.
6. The owner records actions and updates the incident.
7. If the issue is waiting for Temenos, the owner records the follow-up date.
8. If blocked, the owner can raise an escalation.
9. When resolved, the owner records the solution and verification.
10. The incident is closed internally after authorized confirmation.
11. The solution can be converted into or linked to an approved knowledge article.

## 4.5 Incident Management Features

- Incident creation and editing.
- Assignment and reassignment.
- Status history.
- Internal comments.
- Temenos correspondence records.
- Attachments.
- Priority and severity.
- Due dates and follow-up dates.
- Overdue indicators.
- Escalation.
- Related knowledge articles.
- Similar historical incident suggestions.
- Incident search.
- Filtering and pagination.
- Incident reports.

## 4.6 Incident Analytics

Reports should include:

- Total registered incidents.
- Open incidents.
- Resolved incidents.
- Incidents waiting for Temenos.
- Escalated incidents.
- Incidents by module.
- Incidents by priority and severity.
- Incidents by internal owner.
- Average internal resolution time.
- Average time waiting for Temenos, where data is available.
- Recurring problems.
- Root-cause categories.

Resolution-time reports must distinguish time under internal control from time awaiting an external response.

# MODULE 3: DAILY ACTIVITIES AND REPORTING

## 5.1 Purpose

Allow every staff member to record daily work activities through a simple form.

The system automatically organizes these submissions into individual and consolidated team reports.

Staff members should not need to prepare the same information again in Word or Excel.

## 5.2 Daily Activity Fields

| Field | Required | Description |
|---|---|---|
| Activity ID | Automatic | Unique activity reference |
| Employee | Automatic | Logged-in user |
| Report Date | Yes | Date of activity |
| Project | Optional | Related project |
| Task | Optional | Related task |
| Related TSR | Optional | Related incident |
| Activity Title | Yes | Short description |
| Work Performed | Yes | Detailed activity |
| Result / Outcome | Yes | What was achieved |
| Status | Yes | Completed, In Progress, Blocked |
| Challenges | Optional | Issues encountered |
| Next Action | Optional | Planned next step |
| Hours Spent | Optional | Actual time, if required |
| Attachments | Optional | Supporting evidence |

One daily report can contain multiple activities.

## 5.3 Daily Report Workflow

1. Staff member opens Daily Activities.
2. System defaults the report date to the current date.
3. Staff member records one or more activities.
4. Staff member saves the report as Draft.
5. Staff member reviews and submits it.
6. Team Lead reviews submitted reports.
7. Team Lead can approve or return a report with comments.
8. The system includes approved/submitted activities in the consolidated team report according to configured reporting rules.
9. Authorized users generate Word, PDF or Excel reports.

## 5.4 Daily Report Statuses

- DRAFT
- SUBMITTED
- UNDER_REVIEW
- RETURNED
- APPROVED

A submitted report should not be silently overwritten. Changes after submission must create an audit entry and follow the configured correction process.

## 5.5 Report Generation

Supported formats:

- Microsoft Word (.docx)
- PDF (.pdf)
- Microsoft Excel (.xlsx)

### Individual Daily Report

Includes:

- Bank/department heading.
- Employee name.
- Report date.
- Activities performed.
- Related projects and incidents.
- Results.
- Challenges.
- Next actions.
- Reviewer and approval status.

### Consolidated Team Report

Includes:

- Report date.
- Team members who submitted reports.
- Total submitted reports.
- Activities by employee.
- Activities by project.
- Incidents handled.
- Completed tasks.
- Pending work.
- Blockers and escalations.
- Important achievements.
- Management remarks.

### Weekly and Monthly Reports

Includes:

- Activities by date.
- Project progress.
- Task completion.
- Incident trends.
- Escalations.
- Achievements.
- Outstanding activities.
- Recurring challenges.

## 5.6 Report Integrity

- Reports must be generated from saved system records.
- Each export must display its reporting period and generation time.
- Exports must respect user permissions.
- Corrections must be auditable.
- The system must prevent duplicate daily report submissions for the same employee and date unless explicitly configured.
- Team reports must clearly identify missing submissions.
- Templates must be configurable by authorized administrators.

## 8.5 Escalation Workflow

2. Staff member raises an escalation.
3. The system records the source record, reason, impact and required response date.
4. Authorized recipient receives an in-app notification.
5. Recipient acknowledges the escalation.
6. Recipient records decisions or required actions.
7. Responsible staff member updates progress.
8. The escalation is resolved and reviewed.
9. The complete escalation history remains available.

- Overdue reminders.
- Escalation history.
- In-app notifications.
- Management escalation dashboard.
- Link to source incident, project or task.
- Mandatory resolution notes before closure.

Escalation must not duplicate the underlying incident or task. It is a separate record linked to the original work item.

# 4. BUSINESS RULES

## 10.1 General Rules

1. Every important record has a unique identifier.
2. Every record has creation and update timestamps.
3. User ownership is recorded.
4. Important changes are audited.
5. Historical records must not be deleted casually.
6. Related records must maintain referential integrity.
7. Records must respect role and organizational permissions.
8. All dates and timestamps must be stored consistently, preferably in UTC, and displayed in the configured local timezone.
9. All exported reports must be based on authorized data.
10. Required fields must be validated by the backend.

## 10.2 Knowledge Rules

- Only approved articles are generally visible in the published knowledge search.
- Draft articles remain private to authorized users.
- A knowledge article may be linked to multiple incidents.
- A resolved incident may be linked to an existing article or used to create a new one.
- Updating an approved article must preserve its previous version.

## 10.3 Incident Rules

- TSR reference must be unique where the Temenos case is unique.
- Reopened incidents retain their previous history.
- Closing an incident requires resolution information or an authorized exception.
- Incident status changes are recorded.
- An internal status must not be confused with the official Temenos status.

## 10.4 Daily Reporting Rules

- One employee may have one daily report per date.
- One report can contain multiple activities.
- Submitted reports are not silently overwritten.
- Team reports are generated from individual submissions.
- Missing submissions must be visible to authorized managers.

## 10.5 Project and Task Rules

- A task can belong to a project or exist independently.
- A project can have multiple milestones and tasks.
- Task completion and project completion are different states.
- Overdue tasks are calculated from due dates and completion status.
- Blocked tasks should support escalation.

## 10.6 Escalation Rules

- Every escalation must have a reason and responsible recipient.
- Every escalation should be linked to its source record when applicable.
- Closure requires a resolution or decision.
- Escalation history cannot be silently deleted.
- Overdue escalation notifications follow configurable rules.

# 5. DATABASE ARCHITECTURE

## 11.1 Database Design Principles

The platform will use PostgreSQL.

The database should be normalized and organized by business domain.

Recommended principles:

- Use UUID primary keys.
- Use foreign keys for relationships.
- Use database constraints for important business rules.
- Use indexes for frequently searched and filtered fields.
- Use transactions for multi-record operations.
- Use soft deletion where historical preservation is necessary.
- Use explicit status values.
- Store attachment metadata separately from attachment bytes.
- Store sensitive audit information securely.
- Avoid duplicating user, project and incident information in unrelated tables.

## 11.4 Important Relationships

- One user can create many knowledge articles.
- One knowledge article can have many versions and comments.
- One incident can have many updates and status-history records.
- An incident can reference multiple knowledge articles.
- One user can submit multiple daily reports.
- One daily report contains multiple activities.
- A daily activity may reference a project, task or incident.
- One project can have multiple milestones, members and tasks.
- One task may have multiple dependencies.
- One escalation may relate to an incident, project or task.
- One user can receive many notifications.
- Important actions create audit records.

## 11.5 Suggested Key Constraints

- Unique user email or username.
- Unique incident TSR reference, subject to the source system's reference rules.
- Unique daily report per user and report date.
- Unique project code.
- Unique article slug or article reference.
- Foreign keys on all related business records.
- Valid status values.
- Non-negative hours spent.
- Valid date ranges.
- Prevent deleting referenced historical records.

## 11.6 Search Architecture

Use PostgreSQL search capabilities initially:

- Full-text search for titles, descriptions and solutions.
- `pg_trgm` for typo-tolerant matching.
- GIN indexes for searchable text.
- B-tree indexes for references, statuses, dates and foreign keys.

Search priority:

1. Exact TSR/reference match.
2. Exact title/error match.
3. Keyword and full-text match.
4. Fuzzy and related match.

Search must use server-side pagination and must not load all records into the browser.
